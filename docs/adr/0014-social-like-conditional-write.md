# 0014 — 点赞的条件写入与最新意图同步

## 问题

原先每次点击直接并发发送 PUT/DELETE，客户端 generation 只过滤旧响应，没有传给服务器。取消先提交、旧点赞后提交时，服务器最终仍为已点赞。onSettled 的回查也不能撤销写入。

## 决策

替代 ADR 0011 中点赞接口无 body 的约定。帖子、评论使用相同协议：

- `GET /social/posts/:id/like`、`GET /social/comments/:id/like` 返回 `revision`、`likedByMe`、`likeCount`（目前也带 `applied: false`）。
- PUT 表示点赞，DELETE 表示取消；body 必须带 `{ expectedRevision }`。缺失或无效版本返回校验错误，旧客户端不能绕过版本检查。
- 写入返回 `{ revision, likedByMe, likeCount, applied }`。版本不匹配返回 200 + `applied: false` 和当前状态，不修改关系或计数。
- `SocialLikeRevision` 按 `(userId, targetKey)` 保存版本。`targetKey` 为 `post:<id>` 或 `comment:<id>`。取消点赞不删除版本行。
- 在单个 PostgreSQL 事务中 INSERT ON CONFLICT 初始化版本行、SELECT FOR UPDATE 加行锁、比较版本、增删 Reaction、维护计数、递增版本。版本匹配时，即使点赞状态不变也要递增，阻止仍在网络中的旧写入。
- 版本行不关联 Reaction 生命周期；不得单独清除版本后让旧请求继续生效。当前没有版本行清理任务。

移动端每个目标共用一个同步循环，连续点击合并为最新目标。切换依据协调器中的目标而不是尚未重渲染的 props。读版本后条件写入；遇冲突只重试此刻的最新意图。确认的是旧点击时继续同步，不用旧响应刷新 UI。

每次网络等待上限 15 秒；网络错误、408、429、5xx 以 1/2/4/8/15 秒退避重试。超时只结束客户端等待，不假设服务端停止执行。晚到请求携带旧版本，不能覆盖已经确认的新状态。即使 GET 读到目标态，也必须成功执行一次条件写入作为版本屏障，不能直接当作同步完成。

同步中按钮展示最新本地意图；确认时取消相关旧查询并更新缓存。移除原先无版本保护的 onSettled 回查。明确的 4xx 拒绝停止重试、提示用户并刷新数据。退出账号清空内存同步循环。

## 保证范围

同一运行中的客户端、同一用户与目标，在停止点击、网络最终恢复、服务器最终接受操作的前提下，收敛到最新意图。已确认的新状态不会被旧版本请求覆盖。

这不是无条件“最后点击一定成功”：权限拒绝、内容删除、永久断网均不能承诺落库。当前待同步意图不持久化，进程终止会丢失；需要跨重启保证时应增加按账号隔离的持久化 outbox 和恢复同步。多设备之间没有定义人类点击时间的全局排序，CAS 只定义服务器提交顺序；不能把设备时间戳当作可信全局版本。

## 发布与验证

先执行 `20261019090000_social_like_revision` 数据库迁移，再更新 API 和移动端。API 要求新请求协议；旧版客户端点赞需要升级，不能在滚动发布中保留无版本的写入入口。迁移不更改已有点赞关系和计数，已有数据初始版本按 0 处理。

回归测试：移动端协调器验证快速点击、跨组件合并、响应丢失、超时后旧写入、冲突重试、明确失败和退出清理；API 条件写入测试覆盖帖子与评论的乱序、重复请求、同态版本屏障和事务失败，服务入口验证可见性与必填版本。

当前 API 测试使用内存事务替代数据库 IO，未证明真实 PostgreSQL 锁行为。部署前应在测试库并发运行同版本的相反操作，确认仅一个 applied=true，并检查 Reaction 行数和冗余计数一致。
